## Архитектура

`/admin/` → Supabase Auth (почта/пароль) → Cloudflare Worker → GitHub
`content/site.json` и `media/` → GitHub Actions → `render_site.py` → `dist/` → GitHub Pages.

GitHub хранит контент и фотографии; Supabase хранит только учётные записи.
Ни база Sites, ни Pages CMS больше не являются источником данных этого сайта.
Сайт, DNS, домен и GitHub Pages остаются прежними. API размещается на HTTPS
адресе `workers.dev`, поэтому менять DNS сайта не требуется.

У Supabase и Cloudflare Workers есть бесплатные тарифы с лимитами.
Supabase Free может приостанавливать проект после недели бездействия;
для редких входов это ограничение нужно учитывать. Workers Free имеет
ограничения числа запросов и процессорного времени, особенно для фото.
Платные тарифы не включаются автоматически этой интеграцией.
Актуальные условия: https://supabase.com/pricing и
https://developers.cloudflare.com/workers/platform/pricing/.

## 1. Создать сервис входа

1. Войдите в https://supabase.com/dashboard под своим аккаунтом, создайте проект.
   Пароль базы задайте в самом сервисе, не отправляйте его в чат.
2. В **Authentication → Sign In / Providers → Email** включите почту и пароль.
   В настройках отключите публичную регистрацию новых пользователей.
   Минимальную длину пароля установите 12 символов. Оставьте ограничения попыток входа.
3. В **Authentication → URL Configuration** задайте Site URL
   `https://vesnushki-sochi23.ru/admin/` и добавьте этот же URL в Redirect URLs.
4. В настройках API найдите Project URL вида `https://….supabase.co` и
   Publishable key (либо legacy `anon` key). **Не используйте `service_role`**.
5. В **Authentication → Users → Add user → Create new user** создайте свой
   административный аккаунт. Почту и временный пароль вводите в Supabase.
   Скопируйте UUID пользователя для списка разрешённого доступа.
6. Для приглашений и восстановления настройте собственный SMTP в Auth.
   Встроенный почтовый сервис Supabase ограничивает адресатов и доставку;
   отправку клиенту нужно проверить отдельно. Названия пунктов панели могут меняться.

## 2. Создать серверный ключ GitHub

1. Откройте GitHub → **Settings → Developer settings → Personal access tokens →
   Fine-grained tokens → Generate new token**.
2. Resource owner: `korew22220-dev`; Repository access: **Only select repositories**;
   выберите только `vesnushki-sochi`.
3. Repository permissions: **Contents: Read and write**, **Actions: Read-only**.
   Доступ к workflows на запись не нужен: API меняет только контент и фото.
4. Выберите срок действия и сохраните ключ сразу как секрет Worker на следующем шаге.
   После истечения срока его нужно обновить. Не добавляйте его в репозиторий,
   браузер, `admin/config.js`, чат или командную строку с параметром ключа.
5. Используйте обычный fine-grained token владельца или GitHub App installation token.
   **GITHUB_TOKEN из Actions не подходит:** его коммиты обычно не запускают новый push workflow.

## 3. Развернуть API

Откройте эту ветку локально. Нужны Node.js 22+ и Python 3.12+.
Команды выполняются из корня репозитория:

```bash
npm test
python3 render_site.py
cd backend
npx --yes wrangler@4.92.0 login
npx --yes wrangler@4.92.0 secret put GITHUB_TOKEN
npx --yes wrangler@4.92.0 secret put SUPABASE_URL
npx --yes wrangler@4.92.0 secret put SUPABASE_KEY
npx --yes wrangler@4.92.0 secret put ADMIN_USER_IDS
npx --yes wrangler@4.92.0 deploy
```

Каждая команда `secret put` спросит значение в терминале. Вводите его только
туда; не помещайте значения в аргументы команд. `ADMIN_USER_IDS` — один или
несколько UUID пользователей через запятую. Пустой список не разрешает вход.
Пользователь, не входящий в список, не может ни читать панель через API,
ни загружать фото, ни изменять GitHub, даже если зарегистрирован в Supabase.

Эквивалентно можно добавлять значения в Cloudflare dashboard как **Secrets**
в Workers & Pages → этот Worker → Settings → Variables and Secrets.
Установленные в `wrangler.jsonc` переменные:

- `SITE_ORIGIN`: `https://vesnushki-sochi23.ru` — без завершающего `/`;
- `GITHUB_BRANCH`: `main` — рабочий источник и место сохранения.

После deploy сохраните возвращённый HTTPS URL Worker.
В `admin/config.js` впишите только его:

```javascript
window.VESNUSHKI_ADMIN_CONFIG = {
  apiURL: 'https://АДРЕС-ВАШЕГО-WORKER.workers.dev'
};
```

Это общедоступный адрес, не секрет. Никаких ключей в файле быть не должно.
Проверьте сборку и закоммитьте эту конфигурацию в рабочую ветку.
В Worker не сохраняются копии контента и фотографий.

## 4. Опубликовать и проверить

1. Дождитесь успешных проверок pull request. Пока внешние сервисы не настроены,
   оставьте запрос черновиком. Слияние меняет только код и схему сайта, DNS не меняется.
2. После настройки API и `config.js` объедините подготовленный PR в `main`.
   GitHub Pages должен уже использовать **GitHub Actions**, как в текущем проекте.
3. Дождитесь успешного **Publish Веснушки** и проверьте `https://vesnushki-sochi23.ru/`.
4. Откройте `https://vesnushki-sochi23.ru/admin/`. В приватном окне без входа должен
   отображаться только экран входа. API без Bearer-сессии возвращает 401.
   HTML оболочка админки статична и общедоступна; защита применяется к данным и API.
5. Войдите своим аккаунтом. Измените один заголовок, описание и цену,
   загрузите тестовое фото. Проверьте предпросмотр с режимом «Телефон».
6. Нажмите «Сохранить». Убедитесь, что появился **один коммит** с `site.json` и фото,
   затем запустилась сборка и панель показала завершённую публикацию.
7. Проверьте настоящий домен в приватном окне и на физическом телефоне.
   Убедитесь, что заголовок, описание, цена и фото совпадают с сохранёнными.
8. Проверьте меню, Яндекс Форму (не отправляйте лишнюю заявку), окно записи,
   акцию, карусель педагогов, галерею, видео, контакты и юридические окна.
9. Верните тестовые значения через админку и снова проверьте публикацию.
10. Откройте панель в двух окнах. После сохранения в первом второе должно получить
    сообщение о конфликте, а не перезаписать свежие данные.
11. Уберите UUID тестового пользователя из `ADMIN_USER_IDS`, примените настройки:
    следующая попытка сохранения старой сессией должна получить 403.
12. Проверьте смену пароля и письмо восстановления; токен в ссылке должен исчезнуть
    из адресной строки после открытия. Затем создайте аккаунт клиента.

Ни автоматические тесты, ни успешный GitHub Actions сами по себе не подтверждают
настоящий вход и сохранение через настроенный backend. Отметьте все пункты только
после фактического выполнения. Эта проверка требует доступа владельца к сервисам.

## 5. Создать учётную запись клиента

1. Supabase → Authentication → Users → Add user: создайте пользователя с почтой клиента
   и временным паролем либо отправьте приглашение, если SMTP настроен и проверен.
2. Добавьте UUID клиента в `ADMIN_USER_IDS`, сохранив UUID своего аккаунта.
3. Передайте клиенту адрес `/admin/` и временный пароль по отдельному защищённому каналу.
   Не присылайте пароль в этот чат. Приглашение открывает форму установки пароля.
4. Попросите клиента открыть **Изменить пароль** и установить собственный пароль.
5. Для мгновенного отзыва доступа удалите его UUID из `ADMIN_USER_IDS` и примените
   настройки Worker. Дополнительно заблокируйте или удалите пользователя в Supabase.
   API проверяет действительную учётную запись и список UUID при каждом запросе.

## Инструкция для клиента

1. Откройте `https://vesnushki-sochi23.ru/admin/`, введите почту и пароль.
   После перезагрузки страницы потребуется вход снова; сессия хранится только в памяти.
2. В **Разделы сайта** выберите блок и измените текст. Предпросмотр показывает черновик.
   Переключатель «Телефон» меняет ширину предпросмотра. Он не выполняет формы и скрипты.
3. В **Цены** меняйте обычную стоимость. В **Акции** меняйте цену по акции, заголовок,
   условия, последний день и показ всплывающего окна. Скидка рассчитывается из двух цен.
4. В **Фотографии** выберите раздел. Можно заменить снимок, добавить фотографию,
   изменить подпись, порядок галереи или карточку педагога. JPG/PNG/WebP до 8 МБ на входе,
   после автоматического уменьшения до 1800 px — до 2 МБ. SVG загружать нельзя.
5. Фото до сохранения являются черновиками. Нажмите **Сохранить изменения**:
   все используемые новые фото и данные записываются одним коммитом.
   Кнопка **Отменить** возвращает последнюю сохранённую информацию.
6. Дождитесь сообщения о публикации. Проверяйте сайт после обновления страницы;
   доставка новой версии через CDN может занять дополнительное время.
7. Если публикация не прошла, данные могут уже быть сохранены в GitHub. Посмотрите
   **Публикации**; не повторяйте вслепую сохранение после сетевой ошибки.
8. При конфликте скопируйте свои тексты, нажмите **Загрузить свежую версию**, затем
   повторите правки. Сайт не перезаписывает чужие новые изменения.
9. Если сессия закончилась, войдите снова. Открытые правки остаются в редакторе.
   Перезагрузка, закрытие вкладки или подтверждённый выход удаляют несохранённый черновик.
10. Для восстановления пароля введите почту на экране входа и нажмите **Забыли пароль?**.
    Откройте письмо и установите новый пароль.

## Восстановление предыдущего контента

Каждое сохранение — отдельный коммит `CMS: обновить сайт «Веснушки»`.
Владелец может отменить ошибочный коммит через git:

```bash
git pull --ff-only
git revert SHA_ОШИБОЧНОГО_CMS_КОММИТА
git push origin main
```

Перед отменой проверьте, нет ли более поздних полезных правок. Revert запускает
сборку автоматически; удалённые из интерфейса фото остаются в истории GitHub.
Отменяйте именно CMS-коммит, а не миграцию редактора. Схема, генератор и панель
должны оставаться согласованными. Секреты и аккаунты откатом Git не восстанавливаются.

## Технические ограничения и проверки

- Старый `.pages.yml` перемещён в `docs/pages-cms-legacy.yml`: он не совместим с v2.
- Неотредактированный контент перенесён из существующей страницы; неподключённые
  фрагменты остаются в HTML. Все доступные поля схемы имеют реальные маркеры.
- Все изображения проверяются как локальные файлы. Новые загрузки ограничиваются
  форматами/размером и проверкой сигнатуры. SVG загрузки не принимаются.
- CSS, JS, форма Яндекса, canonical, sitemap, CNAME и фотографии сохраняются сборкой.
- Ежедневная сборка и проверка даты в публичном JS отключают завершившуюся акцию.
- В браузере нет GitHub ключа, пароля в хранилище или refresh token. JWT сессии
  существует только в памяти. Supabase ключ Worker — publishable/anon, не service role.
- Фото сначала создаётся как Git blob без коммита. До Save оно не публикуется.
  Сохранение добавляет только фото, которые используются новым контентом.
- Git ref обновляется без `force`; конкурентное сохранение получает конфликт.
- Статистика посещений Sites не переносится на Pages. Вкладка показывает публикации,
  не вымышленные просмотры. Новая аналитика не добавлялась.
- Сохранение пока ограничено 100 новыми фото за раз. Ошибка сети после GitHub PATCH
  требует загрузки свежей версии и проверки истории, чтобы определить результат.
- Автотесты: `npm test`; сборка: `python3 render_site.py`. Проверки без зависимостей npm.
